# URACE

**Universal Recursive Autonomous Co-Founder Engine**

> **It drives the boat. You pick the destination.**

[`URACE`](URACE.md) is an open blueprint and complete portable [install-as-bootstrap](#get-running) specification for continuously improving a [**Product**](#what-is-a-product).

You set the goal and boundaries. URACE handles delegated work, validates results, learns and recovers. It changes itself only with your permission.

```text
BEFORE BOOTSTRAP                         AFTER BOOTSTRAP

YOU + URACE.md + PRODUCT                 YOU — choose the Product and outcome
           │                              │ RETAINS GOAL + AUTHORITY + BOUNDARIES
           ▼                              ▼
       EXECUTOR ── builds ───────► URACE SYSTEM ◄── RESULTS + EVIDENCE ◄── PRODUCT
                                      │                                      ▲
                                      │ autonomously plans and assigns       │ accepted changes
                                      ▼                                      │
                                  EXECUTORS ── propose changes ──► URACE VALIDATES
```

## Why URACE

URACE automates replaceable Executors to improve the Product continuously, measurably and recoverably. It adapts its plans without changing what you control.

## What Is a Product?

A **Product** is whatever URACE improves: a project, service, process, research effort or other goal. It need not be software.

## What Is an Executor?

An **Executor** is an AI agent, orchestrator, program or person that can inspect the Product, change it and run checks. You need one to bootstrap URACE; compatible Executors can then be added, removed, combined or compared. [OpenHands](https://github.com/OpenHands/OpenHands) and [Caveman](https://github.com/JuliusBrussee/caveman) are examples.

## How You Stay in Control

URACE keeps a **Rule Ledger** — a persistent, inspectable record of every rule governing what the system may, must, and must not do. Rules are organized into three immutability levels:

- **L0 PURPOSE** — immutable; defines why the system exists
- **L1 DIRECTIVE / PERMISSION / PROHIBITION** — durable; only you can add or change these
- **L2 OBJECTIVE / POLICY** — operational; the lifecycle manages these within your delegated boundaries

Every accepted change is bound to a snapshot of the active rules at the moment it was made. You can inspect the full rule graph, trace which rules governed any past change, and surface conflicts at any time without an Executor call.

## Get Running

1. Give [`URACE.md`](URACE.md) to a capable Executor with access to your Product.
2. Say **“Bootstrap.”**
3. Follow the setup to define the outcome, delegation and protected boundaries.

`URACE.md` is the only required bootstrap document. Setup validates the result, keeps its system files under `urace/`, and activates a repository-local `urace` command from the Product folder. If `direnv` is installed, the command loads automatically whenever you enter the folder and is removed from `PATH` when you leave; otherwise run it directly as `./urace/.urace/bin/urace` or `python3 -m urace` from within `urace/runtime/`.

> **Bootstrap artifact stability:** Bootstrapping from the same `URACE.md` produces a functionally equivalent runtime on each run, but generated artifacts are not byte-for-byte reproducible between distinct bootstrap invocations. Compare builds through `urace check` output and behavior rather than artifact hashes. Where the update path is available and validated, `urace update` is preferable to re-bootstrapping an existing system.

> **Interrupted bootstrap:** If the bootstrap was interrupted before completing setup, run `urace check` before issuing any commands. URACE reports whether an incomplete bootstrap transaction remains pending and whether `urace autonomous` can complete it. Do not re-run the bootstrap prompt while a prior incomplete transaction is unresolved; doing so starts a second lifecycle instead of completing the first.

## Use It

Generated help lists the commands supported by your implementation.

```text
urace check                     inspect lifecycle state
urace vitals                    inspect progress, cost and health
urace autonomous                run persistent evolution
urace help executor             learn how to inspect, attach or detach Executors
urace help configuration        learn how to inspect or change configuration
urace add-goal ...              queue a measurable goal
urace intent add "…"            add a durable directive (what to pursue)
urace constraint add "…"        add a hard constraint (what not to do)
urace constraint add "…" --allow add an explicit permission (what is delegated)
urace rules list                list all active governance rules
urace rules conflicts           surface detected rule conflicts
urace update download ...       store a new version without changing the system
urace update explain ...        review its local effects without changing files
urace update apply ...          validate and activate the new version
urace update resolve ...        resolve a blocked update conflict
```

You can edit the Product while URACE runs; it preserves newer work instead of overwriting it. Read-only commands (`check`, `vitals`, `commands`, `inbox list`, `goal list`, `change list`, and all `help` operations) load an atomic state snapshot and can run freely from a second terminal while `urace autonomous` owns the lifecycle. Mutating commands (`add-goal`, `update apply`, `configuration`, and similar) write to an atomic inbox and are applied exactly once at the next safe lifecycle boundary; they never conflict with each other or with an active autonomous run.

> **No Executor available:** If no capable Executor is configured or the only configured Executor is permanently unavailable (not a temporary capacity pause), URACE enters `DORMANT` or blocks only Executor-dependent work rather than losing lifecycle ownership. Durable state, Authority and lifecycle history are preserved. Use `urace help executor` to inspect attached Executors, attach a new one, or switch to a compatible alternative. Executor-independent operations such as `urace check`, `urace vitals` and read-only commands remain available regardless of Executor state.

> **Budget exhaustion:** When a metered Executor exhausts its configured hard budget, URACE stops Executor-dependent work and enters dormancy rather than continuing to incur cost. Use `urace vitals` to inspect remaining budget, cost-per-accepted-change and the exhausted boundary. Resuming Executor-dependent work requires an authorized budget adjustment via `urace help configuration`; direct edits to generated state files are not a valid corrective action. The lifecycle retains its current task reservation and durable state; no work is lost when a budget boundary is reached.

> **Queued inputs during BLOCKED state:** When the lifecycle is `BLOCKED`, queued authoritative inputs — including `urace add-goal`, `urace update apply`, configuration changes and similar mutating commands — are preserved in the atomic inbox and are not lost or discarded. They are applied at the next safe lifecycle boundary after the blocking state is resolved. Use `urace check` to confirm the blocking state is resolved before expecting queued inputs to take effect. Do not re-issue an identical command assuming the first was lost; a duplicate input will be applied twice — as two separate authorized actions — at separate lifecycle boundaries.

> **Pending queued input inspection:** When you are unsure whether a mutating command was received before a stop, restart, or `BLOCKED` state, run `urace inbox list` to inspect what inputs are currently pending application. An input visible in the inbox is queued for the next safe lifecycle boundary and must not be re-issued; a duplicate re-issue applies it a second time as a separate authorized action. An input absent from the inbox and not yet reflected in lifecycle state may be re-issued safely. Inbox entries persist through restarts and are removed only after their effects are durably committed to accepted state; an entry visible after a restart confirms the command survived the interruption.

> **Queued input processing order after unblocking:** When the lifecycle exits `BLOCKED` state and begins applying previously queued inputs, they are applied in the order they were received — oldest first. Multiple queued inputs accumulated during a `BLOCKED` period are each applied at successive safe lifecycle boundaries in receipt order; no input is re-ordered, promoted or deferred based on its content type, target scope or command class. An operator observing a sequence of queued inputs taking effect after a block resolves should expect the exact receipt order to be preserved throughout the catch-up sequence.

Inspect more commands with `urace` or `urace help`.

## Update Safely

Keep the current `URACE.md` version identifiable, then use `urace update`:

1. `download` stores the identified new version separately without changing the working system.
2. `explain` reports the new version's changes, local effects and risks without changing files.
3. `apply` preserves compatible tracked changes and activates the new version only after validation and a health check.
4. `resolve`, only after a conflict, records your decision and resumes the same update.

The `explain` and `apply` commands detect tracked configuration and implementation changes, including changes made by other agents. A conflict applies no files and waits for your decision; failed activation rolls back. Never edit generated state files or copy specification changes into runtime files; use `urace help update`.

The `apply` and `resolve` commands require permission to update URACE. They are queued for the next safe checkpoint; run `urace autonomous` to process them.

> **Update queued during BLOCKED or PAUSED lifecycle:** When `urace update apply` or `urace update resolve` is queued while the lifecycle is `BLOCKED` or `PAUSED`, it is preserved in the atomic inbox and is not lost. It will not be applied until the blocking or paused condition is fully resolved; the update takes effect only at the next safe checkpoint that follows resolution. Do not interpret the update's absence from active processing as a failure, timeout or dropped command; `urace check` will confirm the update is pending and identify which lifecycle condition must resolve before it can be applied.

> **Specification vs runtime scope:** Authorizing URACE to evolve its running implementation does not authorize modification of `URACE.md`. These are distinct evolution scopes: specification changes require explicit Authority at that scope and proceed only through the `urace update` lifecycle. Autonomous self-evolution changes the running implementation; it does not and cannot rewrite the bootstrap specification without that separate Authority.

> **Update command validation status:** The `urace update apply` and `urace update resolve` commands apply specification deltas incrementally and are under active validation. Delta-application behavior across distinct generated builds has not been demonstrated reliable as the default update path. Verify the installed system with `urace check` after any `apply` or `resolve`, and retain the previous `URACE.md` until the result is confirmed functional. Re-bootstrapping from a new `URACE.md` remains a valid fallback when the update path is blocked or produces unexpected results.

> **`urace update explain` error or incomplete output:** If `urace update explain` returns an error, exits with a non-zero status, or produces visibly incomplete output rather than a full effects report, treat it as a blocking condition and do not proceed to `urace update apply`. The most common causes are the same as for `urace check` errors: transient state-snapshot lock contention (wait briefly and retry) or a storage issue requiring recovery. If the error persists, follow `urace help update` or `urace help recovery`. Retain the current `URACE.md` and the currently running system until `explain` returns a complete assessment; an inconclusive effects report is not a safe basis for `apply`.

> **Pending downloaded update:** When `urace update download` has stored a new version candidate but `urace update apply` has not yet been run, `urace check` reports the pending version identifier and its download timestamp. A pending candidate does not block `urace autonomous` or ordinary Product evolution — the running system continues unchanged. Multiple downloads of the same version identifier are idempotent; downloading a second distinct version while one is already pending preserves both candidates; run `urace update explain` against each before deciding which to apply. A downloaded candidate is not applied automatically and does not expire; operators are responsible for progressing it through `explain` and `apply` or explicitly clearing it when it is no longer relevant. `urace check` continues to surface an unresolved pending candidate until it is applied, superseded by a newer downloaded version, or explicitly cleared.

> **Clearing a pending downloaded update:** When a downloaded version candidate is no longer relevant — for example, because you have decided to retain the current version or a newer candidate supersedes it — use `urace help update` to identify the supported clearance command for your installed version. Clearing a candidate removes its stored version file and its entry from `urace check` output without affecting the running system, accepted changes, or other pending candidates. Do not delete a stored version file directly outside the lifecycle boundary; direct deletion leaves an orphaned `urace check` entry that can only be resolved through recovery. If no clearance command is available in your installed version, retaining the unused candidate is safe — it does not affect ongoing evolution.

> **Corrupted downloaded update candidate:** When `urace check` surfaces a pending version identifier but `urace update explain` fails with a structural parse or read error that persists after a brief retry — as distinct from a transient lock-contention error — the stored version file is likely corrupted or incomplete from an interrupted download. A persistent structural error requires re-downloading the candidate rather than retrying `explain`: use `urace update download` with the same version identifier to replace it; the download is idempotent for that identifier. Distinguish this from a transient `explain` error (lock contention clears on retry) or a deliberate clearance case. Do not run `urace update apply` with a candidate that `explain` cannot successfully parse; an unreadable candidate is not a safe basis for `apply`, and attempting it produces a conflict or failure requiring recovery.

> **Update conflict resolution:** When `urace update apply` or `urace update resolve` reports a conflict, run `urace update explain` with the conflicting version before taking any resolution action. The explain output identifies which locally tracked changes or configuration entries the incoming specification would replace or overwrite. Do not run `urace update resolve` until you have reviewed that output and confirmed your decision preserves applicable normative invariants. A conflict that cannot be resolved without weakening a MUST rule must not be resolved by choosing the weaker path; in that case, retain the current `URACE.md` until a compatible new version is available, or re-bootstrap from the new version when feasible after preserving durable lifecycle state.

> **Re-bootstrap preserves lifecycle history:** Re-bootstrapping from a new `URACE.md` reconstructs the running implementation only — not durable lifecycle state. Governance records, accepted changes, Intent, Authority, Evidence, history and Product artifacts under `urace/state/` are preserved and migrated into the reconstructed runtime. Re-bootstrap is a validated runtime replacement, not a reset. Use `urace check` after completion to confirm that durable state and Authority boundaries are intact before resuming `urace autonomous`.

> **Interrupted re-bootstrap:** If `urace update apply` or a subsequent re-bootstrap was interrupted before completion, run `urace check` before any further action. The launcher preserves the prior stable runtime when the incoming candidate cannot start, start-confirm, or complete its activation health check. `urace check` reports whether an incomplete re-bootstrap transaction remains pending, whether durable lifecycle state is intact, and which runtime is currently active. Do not re-issue the bootstrap prompt while a prior incomplete re-bootstrap transaction is unresolved; the existing stable runtime and durable lifecycle state remain valid, and re-issuing the bootstrap prompt creates a second lifecycle rather than completing the first.

> **Failed update activation health check:** When `urace update apply` reaches the activation gate — the new runtime starts successfully — but the post-activation health check fails, URACE restores and restarts the prior stable runtime without operator intervention and records the failed activation as Evidence. `urace check` surfaces an activation-failed disposition identifying the failing health criteria and confirms the prior stable runtime is active. The failed candidate remains as a downloaded version pending operator review; use `urace update explain` to re-examine it and determine whether a corrective re-download or explicit clearance is appropriate before attempting `urace update apply` again. This is distinct from an interrupted re-bootstrap — where the process terminated before reaching the health gate — because here the candidate was evaluated and did not pass. Do not re-run `urace update apply` with the same candidate without first understanding the health failure surfaced in `urace check`.

## See Progress

URACE reports observed **metrics**, system-health **vitals** and decision **scores**. Inspect them with `urace check`, `urace vitals` and `urace change list`; use `urace help` for details.

> **`urace change list` output:** `urace change list` presents accepted increments in reverse chronological order. Each entry includes the stable change identity, its governing Objective or Plan reference, the validation disposition, affected artifact identifiers, resource cost and current attribution state. Attribution state progresses from `UNATTRIBUTED` as follow-up observations accumulate; the list reflects each change's attribution as of its most recent follow-up. `urace change list` is read-only and does not invoke an intelligent Executor or advance the lifecycle. Use `urace help change list` for filtering, sorting and detail options.

> **Goal forecast interpretation:** `urace goal forecast` reports advisory completion ranges derived from declared estimate parameters, comparable completed goals, or an explicitly labelled estimated-cost proxy when neither is available. Forecast output is confidence-qualified and does not invoke an Executor. It does not create delivery commitments, Authority or acceptance gates. A low-confidence or proxy-labelled range reflects insufficient prior comparable history; supplement it with schedule information via `urace goal schedule` rather than treating it as an authoritative deadline. Ranges widen appropriately when blocking conditions, dependency chains or unresolved effects are present; inspect those blockers with `urace check` before concluding that a goal is infeasible.

> **Note for operators:** Stopping `urace autonomous` (Ctrl+C, system restart, or resource constraint) does not end lifecycle ownership. Dormancy is valid autonomous operation; the lifecycle persists in durable state and restarting resumes it rather than creating a new one. Run `urace check` after any restart to inspect the current lifecycle state before taking further action.

> **Graceful stop output:** When `urace autonomous` exits gracefully after a stop signal, inspect its final output before resuming: URACE reports whether durable lifecycle state was fully committed and identifies any unresolved effects, pending reservations or queued inputs that require attention before the next run. If the final output indicates durable state was not confirmed — or is absent because the process was terminated abruptly — run `urace check` before issuing any new mutating commands. Do not re-issue a command that was already queued before the stop without first confirming its inbox status with `urace check`; a command preserved in the atomic inbox will be applied at the next safe boundary, and re-issuing it without confirmation applies it a second time as a separate authorized action.

> **Graceful stop and unapplied inbox inputs:** When `urace autonomous` exits gracefully, its stop output identifies queued authoritative inputs that were received before the stop signal but not yet applied at the stop boundary. This identification is the primary surface for determining whether re-issuing a specific command would constitute a duplicate authorized action — you do not need to separately run `urace inbox list` to make that determination from a clean graceful stop. If the stop output is absent or incomplete because the process was terminated abruptly rather than gracefully, treat all inputs queued before the termination as potentially unapplied and use `urace inbox list` directly to inspect pending items before re-issuing any command.

> **Measurement integrity:** Once a goal's baseline and measure are established, changing the measure, target, or cadence requires retaining the prior values with provenance — not overwriting them. To correct an incorrectly scoped baseline, use an authorized lifecycle operation (such as `urace add-goal` with updated parameters) that appends a new record rather than replacing the existing one. Direct edits that silently rewrite a baseline or achieved result violate measurement integrity.

> **Executor unavailability:** When a provider's capacity is exhausted or a shared execution environment becomes unavailable, URACE enters scheduled dormancy — not a failure or candidate regression. The lifecycle retains the current task and its reservation. Use `urace check` to distinguish capacity-wait dormancy (a scheduled retry window is present) from no-justified-work dormancy (no pending reservations). The lifecycle resumes automatically when capacity returns; no manual restart is needed unless the lifecycle itself has stopped through one of the explicit conditions listed under `urace help autonomous`.

> **Executor re-authentication after capacity restoration:** When an Executor returns from a provider-capacity unavailability period, URACE performs a non-model authentication probe before that Executor receives any new work assignments. Prior authentication state observed before the unavailability period is not assumed valid; provider capacity resets may accompany session expiry, token rotation, or credential changes that are independent of the capacity restoration event. A brief delay between capacity restoration and work resumption is therefore expected and normal. If the probe fails, the Executor is held in a configured-but-not-authenticated state even though provider capacity has returned; URACE will not dispatch new work to it until a successful probe confirms current authentication. Use `urace check` to distinguish this probe-pending state — where capacity is available but authentication has not yet been confirmed — from capacity-wait dormancy — where provider capacity itself has not yet returned. Do not attempt a manual restart or re-attach the Executor while it is in probe-pending state; the probe sequence completes without operator intervention when credentials are valid.

> **Waiting for Executor capacity:** `WAITING_FOR_CAPACITY` in `urace check` output means a scheduled or reserved Operation cannot proceed because the required Executor is capacity-exhausted at the provider. This is distinct from `BLOCKED` (an Operation has an unreconciled externally committed effect), `DORMANT` (no reserved work exists now), and `WAITING_FOR_AUTHORITATIVE_DECISION` (a decision was retained by the authoritative source). The lifecycle retains its task reservation and no work is lost. Use `urace check` to inspect the specific Executor and the reserved Operation awaiting capacity, and `urace vitals` to review remaining budget. The lifecycle resumes automatically when provider capacity returns; no manual restart or new duplicate commands are needed.

> **Waiting for precondition:** `WAITING_FOR_CONDITION` in `urace check` output means a reserved Operation cannot proceed because a required precondition is not yet satisfied — distinct from `WAITING_FOR_CAPACITY` (Executor capacity ceiling), `WAITING_FOR_SCHEDULE` (time-based trigger not yet due), and `WAITING_FOR_AUTHORITATIVE_DECISION` (decision retained by the authoritative source). `urace check` must expose three fields without an Executor call: the awaited condition and the observable criterion constituting its satisfaction, the identity of the dependent Operation gated on that condition, and the earliest qualifying resolution path. If no observable resolution path exists, the condition is unresolvable and surfaces as a named blocking limitation requiring operator intervention. Durable state and task reservations are preserved intact. The lifecycle resumes automatically when the awaited condition is met; do not restart `urace autonomous` or re-issue commands as the resolution path.

> **Waiting for scheduled time:** `WAITING_FOR_SCHEDULE` in `urace check` output means the lifecycle has reached a point where the next eligible boundary is determined by a time-based trigger that has not yet become due — distinct from `WAITING_FOR_CONDITION` (a precondition not yet satisfied), `WAITING_FOR_CAPACITY` (Executor capacity exhaustion), and `WAITING_FOR_AUTHORITATIVE_DECISION` (a decision retained by the authoritative source). `urace check` identifies the scheduled trigger, its due time, and the lifecycle scope that depends on it. No manual action is required: the state exits automatically when the scheduled time arrives. If the due time appears incorrect or the schedule seems stale, use `urace help` for the appropriate corrective operation; do not restart `urace autonomous` to force earlier evaluation.

> **Executor capability gap:** When an Executor is present, authenticated and within budget but does not support a capability required for a planned Operation, URACE surfaces a named capability gap in `urace check` output. A capability gap blocks only the Operations that require the missing capability; Executor-independent work and Operations the attached Executor can fulfill continue uninterrupted. This is distinct from Executor unavailability (where provider capacity is exhausted), budget exhaustion (where a hard spending limit is reached), and authentication failure (where credentials are not confirmed). Use `urace help executor` to inspect which capabilities are required and attach an Executor that provides them; attaching a capable Executor resolves the gap without interrupting the lifecycle.

> **Pending-validation backlog after validation capability restoration:** When a validation system that was temporarily unavailable becomes available again, URACE processes all Observations that were preserved in pending-validation state during the outage. This produces a burst of validation activity immediately after the restoration event — this is correct ordered backlog processing, not a replay, duplication, or regression. No new incoming Observation is required to trigger this processing; the restoration event itself is the qualifying condition. Use `urace check` to confirm that the validation backlog is draining and that no Observation has been automatically accepted by elapsed time or Executor re-confirmation in place of independent validation.

> **Validating lifecycle state:** `VALIDATING` is active when URACE has completed an Operation and is executing the acceptance validation required before that Product increment can be committed to the accepted Product state. `VALIDATING` is distinct from `ACTIVE` — which executes work to produce an increment — and from `ASSESSING` — which evaluates whether justified work exists before any increment is produced. An increment held in `VALIDATING` is not yet accepted; the Product baseline does not advance until validation succeeds. Use `urace check` to identify the specific increment under validation, the validation method, and the current validation step. No operator action is needed during a normal `VALIDATING` cycle; if validation fails, the lifecycle enters `REPAIRING` rather than silently discarding the increment. Do not restart `urace autonomous` or manually edit Product files while `VALIDATING` is active.

> **Blocked lifecycle state:** `BLOCKED` is distinct from `DORMANT`: a `DORMANT` lifecycle has no justified work now but retains a follow-up condition, whereas a `BLOCKED` lifecycle has an Operation with an unreconciled uncertain external effect that prevents forward progress. Do not restart `urace autonomous` or retry the affected Operation while the lifecycle reports `BLOCKED`; doing so risks duplicating a consequential effect or overwriting unreconciled state. Use `urace check` to identify the specific unresolved effect and the reconciliation path, then follow the displayed guidance before resuming autonomous operation.

> **Reconciling committed effect:** `RECONCILING` in `urace check` output means URACE has positively established that the qualifying condition for resolving a previously uncertain externally committed effect is met and is actively executing the reconciliation queries, probes or transaction-reference lookups required to establish a definitive disposition. This is distinct from `BLOCKED` — which halts because reconciliation cannot yet begin — since `RECONCILING` represents active in-progress resolution work. Do not restart `urace autonomous`, retry the affected Operation, or issue a mutating command whose effect depends on the uncertain outcome while `RECONCILING` is active; doing so risks duplicating a consequential effect or overwriting the reconciliation record in progress. The lifecycle advances to the appropriate post-reconciliation state automatically when a definitive disposition is established. If `RECONCILING` persists beyond expected bounds without a disposition, `urace check` surfaces a named reconciliation-stalled condition identifying the specific blocking reason and the earliest qualifying condition for resumption.

> **Expired opportunity window:** When a finite opportunity window — established by Intent, policy, Evidence or constraints — expires while dependent Objectives remain active or committed effects remain unreconciled, `urace check` surfaces a named constraint-change event and lists the open unreconciled effects as named blockers. An expired window does not automatically retire an Objective or authorize rollback of committed effects; it introduces a constraint-change Trigger that requires proportionate reassessment. Do not manually retire Objectives or edit state files to resolve the expiration; follow the displayed reconciliation guidance before resuming `urace autonomous`.

> **Paused lifecycle state:** `PAUSED` is distinct from `BLOCKED` and `DORMANT`: a `PAUSED` lifecycle has been explicitly suspended by an authorized operator command and is not actively processing work, but retains durable state, Intent, Authority and lifecycle history intact. Unlike `BLOCKED`, it has no unreconciled externally committed effect requiring resolution; unlike `DORMANT`, its suspension was explicit rather than the result of no justified work existing now. Use `urace check` to confirm the paused state and inspect what work was in progress at suspension. Resume with `urace autonomous`; the lifecycle re-enters its ordinary assessment cycle from the durable state preserved at the pause boundary.

> **Scheduled conditions accumulated during BLOCKED or PAUSED:** Scheduled conditions that become due while the lifecycle is in `BLOCKED` or `PAUSED` state are not lost. They are durably queued and will be evaluated at successive eligible lifecycle boundaries in the order they became due, before new unscheduled work is started after `PAUSED` resumption. If you observe a burst of scheduled work executing sequentially after resolving a `BLOCKED` or `PAUSED` period, this is correct ordered catch-up behavior — not a replay, duplication, or regression. Do not intervene to stop or restart the lifecycle during this sequence; each execution is a distinct authorized action advancing the backlog in due-date order.

> **Waiting for a retained decision:** `WAITING_FOR_AUTHORITATIVE_DECISION` is distinct from `BLOCKED` and `DORMANT`: the lifecycle has reached an operation where a decision was explicitly retained by the authoritative source and cannot be delegated. URACE pauses only the dependent workstream — not the entire lifecycle — and continues unrelated delegated work. Use `urace check` to identify which decision is outstanding and what input is expected. This state MUST NOT become the normal operating mode; if it persists unexpectedly, verify that delegation boundaries in Authority configuration match your intended autonomy.

> **Queued mutating inputs during WAITING_FOR_AUTHORITATIVE_DECISION:** When the lifecycle is in `WAITING_FOR_AUTHORITATIVE_DECISION`, operator-submitted mutating commands — including `urace add-goal`, `urace update apply`, configuration changes and similar — are preserved in the atomic inbox and are not lost. Because `WAITING_FOR_AUTHORITATIVE_DECISION` suspends only the dependent workstream rather than the entire lifecycle, an inbox input whose effects are independent of the awaited decision may be applied at the next safe lifecycle boundary reached by an unblocked workstream; an input with a direct or transitive dependency on the awaited decision is deferred until after the decision is provided, in receipt order. Use `urace inbox list` to confirm receipt of any queued command. Do not re-issue an identical command assuming the first was lost; a preserved inbox entry will be applied a second time as a separate authorized action if re-issued.

> **Scheduled conditions during WAITING_FOR_AUTHORITATIVE_DECISION:** When the lifecycle is in `WAITING_FOR_AUTHORITATIVE_DECISION` and a scheduled condition becomes due, its handling depends on whether it has a direct or transitive dependency on the retained decision. Conditions whose workstreams are unblocked continue to be evaluated at their due times without interruption — `WAITING_FOR_AUTHORITATIVE_DECISION` suspends only the dependent workstream, not the entire lifecycle. Conditions that are themselves dependent on the same retained decision are durably queued and will be evaluated at successive eligible lifecycle boundaries after the awaited decision is provided, in the order they became due. Use `urace check` to distinguish which scheduled conditions are queued pending the retained decision from those continuing normally in unblocked workstreams. If you observe a burst of dependent scheduled work executing after providing the awaited decision, this is correct ordered catch-up behavior — not duplication or regression.

> **Evidence-blocked inspection:** When the most recent assessment cycle could not complete because Evidence was absent or below threshold, `urace check` exposes four fields rather than a generic absence notice: (a) the specific Evidence dimension that was missing or insufficient; (b) a quantified shortfall where determinable — for example, minimum required observations versus observations available; (c) whether lifecycle advancement is currently blocked pending that Evidence; and (d) the earliest condition or qualifying event that would allow reassessment to proceed. Reporting only that an aggregate is withheld does not substitute for these four fields. If `urace check` shows an evidence-blocked status, supply or configure the identified Evidence source before expecting the lifecycle to advance.

> **Resource-sink detection:** URACE periodically identifies resource sinks — repeated no-effect work, unused connectors, stale goals, oversized prompts, redundant checkpoints and excessive state or documentation growth — and surfaces findings through `urace vitals`. Sink findings are measurable and reviewable; they are not inferred from artifact size alone. Use `urace vitals` to inspect current sink observations and corrective-action status. Addressing an identified sink requires an authorized lifecycle operation; direct deletion of state files or prompt content outside the ordinary command boundary is not a valid corrective action.

> **Discovery-loop yield in vitals:** `urace vitals` exposes a `discovery_yield_exhausted` field under `executor_credit_usage`, together with the current unproductive streak, the configured exhaustion threshold, and productive-yield rates over 24h and 30d windows. These fields are present regardless of whether the exhausted condition is active; a low yield rate is a valid early-warning signal before the threshold is reached. The `status` field shows `DISCOVERY_YIELD_EXHAUSTED` when the streak has reached the threshold and ordinary scheduled discovery is blocked. Use these fields to distinguish routine dormancy between scheduled discovery cycles — where the streak has not reached the threshold — from discovery-yield exhaustion — where further credits are withheld until a qualifying reset occurs.

> **DISCOVERY_YIELD_EXHAUSTED:** `DISCOVERY_YIELD_EXHAUSTED` in `urace check` or `urace vitals` output means the discovery loop has run consecutively without producing justified work a number of times equal to or greater than the configured threshold, and URACE has stopped spending credits on scheduled discovery cycles at ordinary cadence. This is not a failure: the lifecycle remains dormant and durable state is intact. Further discovery resumes automatically when a qualifying reset event occurs: a new goal added via `urace add-goal`, a new Evidence record, a change to governing Intent or product files, or an explicit `urace autonomous --force-discovery` invocation. Do not restart `urace autonomous` alone without one of these qualifying inputs; an unqualified restart wakes the lifecycle but URACE will block the discovery call and remain dormant rather than spending a credit. If you believe new justified work exists but URACE has not detected it, use `urace add-goal` to supply new measurable input or run `urace autonomous --force-discovery` to issue an attributed override invocation; both qualify as reset events.

> **Discovery backoff and proportionality:** Before spending a discovery credit, URACE checks whether the expected marginal discovery value at the current product state justifies the cost. This proportionality assessment accounts for the recent productive-yield rate, the current unproductive streak, whether new input has arrived since the last cycle, and whether a known blocking condition — such as an exhausted execution budget or an active `BLOCKED` state — would prevent acting on any discovered work regardless of outcome. If the assessment finds insufficient expected value, the cycle is deferred without spending a credit. The proportionality outcome — invoked or deferred, and on what basis — is recorded in the inspection output. You can inspect the last proportionality decision via `urace check`; the defer reason identifies which condition lowered expected value below the threshold. If URACE is deferring cycles you believe should run, the most reliable corrective action is to supply new input via `urace add-goal` or an inbox command rather than forcing a credit spend without new justified context.

> **Check vs Vitals distinction:** `urace check` reports lifecycle state, capability readiness, blockers and unresolved effects. `urace vitals` reports progress metrics, evolution efficiency, Executor usage, resource-sink findings and the overall system scorecard. For routine health monitoring use both: `urace check` identifies what is blocked or unresolved, and `urace vitals` identifies whether evolution is producing measurable progress proportionate to resource use. Neither command invokes an intelligent Executor or advances the lifecycle.

> **Vitals cost accounting units:** `urace vitals` reports cost-per-accepted-change using the strongest available measurement. When provider-reported monetary or token data is unavailable — as may be the case with some Executor adapters — an explicitly labelled call-count proxy is used instead. Check the unit label shown by `urace vitals` before drawing billing or credit-planning conclusions; a proxy figure does not represent provider-side monetary cost without a conversion that URACE cannot supply. Where provider-reported usage later becomes available, vitals reflects the stronger measure and labels the change.

> **`urace check` error or incomplete output:** If `urace check` returns an error, exits with a non-zero status, or produces visibly incomplete output rather than a lifecycle state report, the most common causes are transient state-snapshot lock contention (a running `urace autonomous` instance holds the read lock — wait briefly and retry) or a storage issue requiring recovery. Do not issue mutating commands after an inconclusive `urace check` result; do not re-bootstrap solely because `urace check` returned an error. If the error persists after a brief retry, confirm whether a `urace autonomous` process is running. If no process is running and the error persists, follow the guidance surfaced in the error output or `urace help recovery` — do not edit state files directly.

> **Lifecycle repair in progress:** `REPAIRING` in `urace check` output means URACE is actively executing a bounded Product-repair sequence following an integrity check failure or activation health check failure. `REPAIRING` is distinct from `ACTIVE` — ordinary Product evolution under authorized Intent — and from `BLOCKED` — which holds an unreconciled externally committed effect requiring operator-guided resolution before proceeding. The lifecycle entered `REPAIRING` autonomously after an attributable integrity or health signal; no operator action is needed to initiate the repair. Do not restart `urace autonomous` or manually edit state or artifact files while `REPAIRING` is active; the repair sequence has its own transactional activation and stable-rollback path, and direct edits bypass it. Use `urace check` to confirm which integrity criterion or health check triggered repair and what the current repair step is. When `REPAIRING` exits successfully, `urace check` confirms restoration and the lifecycle returns to ordinary assessment; if the repair sequence exhausts its declared attempt ceiling without success, `urace check` surfaces a named repair-exhausted condition and the recovery path before any resumption of `urace autonomous`.

> **Assessing lifecycle state:** `ASSESSING` is the evaluation phase in which URACE performs an independent review of current Evidence, outstanding Objectives, pending reservations, and resource availability before committing to new work. The lifecycle enters `ASSESSING` on wake from `IDLE` (`DORMANT`), on successful exit from `REPAIRING`, and at any state transition requiring independent justification before active execution begins. `ASSESSING` is distinct from `ACTIVE` — which executes work under a positively identified justified Objective — and from `IDLE`, which holds no justified work and no active evaluation. Use `urace check` to confirm the current assessment scope and which Objectives are under evaluation. No operator action is needed during a normal `ASSESSING` cycle; the lifecycle advances to `ACTIVE` or `IDLE` through its own assessment outcome without restart.

> **Product integrity recovery:** When `urace check` reports that the working Product failed integrity validation and URACE has restored or attempted to restore the last-known-stable accepted version, confirm that the restoration completed successfully before resuming `urace autonomous`. Use `urace check` to identify which accepted checkpoint served as the recovery boundary and whether any unresolved effects remain. If the failed increment can be repaired through an authorized lifecycle operation, use the ordinary Objective and Plan path rather than manually re-applying the failed change outside the lifecycle. Manually editing restored files to re-introduce a change that failed validation bypasses the acceptance boundary and creates an inconsistent accepted state.

> **Inconsistent lifecycle state:** If `urace check` reports a lifecycle state that appears internally inconsistent — for example, `ACTIVE` with no current Objective, `BLOCKED` without an identified unresolved effect, or `DORMANT` with a pending reservation that should have triggered reassessment — do not attempt to resolve the inconsistency by directly editing state files. Use `urace check` to inspect the full state vector and follow any displayed reconciliation guidance. If guidance is absent and the inconsistency persists, run `urace autonomous` to allow the lifecycle to perform a fresh assessment cycle; the ordinary lifecycle reconciliation path resolves most transient inconsistencies without operator state intervention. Direct state-file edits outside the lifecycle boundary may create inconsistencies that outlast the original problem and cannot be surfaced by `urace check`.

> **Wake-integrity gap after restart:** A wake-integrity gap in `urace check` output means a recorded wake registration — a scheduled trigger, OS callback, file-system watcher or equivalent — could not be verified as active in the current environment after restart. This is a named limitation, not a lifecycle failure: durable state, Authority, Intent and lifecycle history remain intact. URACE retains lifecycle state and remains available to restart-based reassessment without data loss until each unverifiable registration is re-established or explicitly documented as unavailable. Do not re-bootstrap or edit state files to resolve a wake-integrity gap. Instead, confirm that the environment supports the required wake mechanism, re-establish the registration where feasible, and resume `urace autonomous` once confirmed. The gap clears from inspection output only after the registration is re-verified.

> **Unresolved ownership boundary:** When `urace check` surfaces an unresolved ownership boundary, a prior lifecycle process holds a state lock whose liveness — whether that process is still alive — cannot be established through available environment signals such as process existence or heartbeat record age. Elapsed time alone does not resolve an unresolved ownership boundary; URACE will not silently supersede it. To acquire ownership, use the authenticated lifecycle clearance command identified in `urace check` output; this records the clearance as a durable event and is the only valid path when liveness is indeterminate. Do not delete the lock file directly outside the lifecycle boundary; direct deletion bypasses the durable clearance record and may produce inconsistent state that outlasts the original contention. An unresolved ownership boundary is distinct from `BLOCKED` (which has an unreconciled externally committed effect) and from `PAUSED` (which was explicitly suspended by an authorized operator command).

> **Decision record provenance revision:** When Evidence cited as primary justification for an accepted decision is later found to have been fabricated, provably incorrect, or formally retracted by its source, `urace check` surfaces the affected Decision Record as provenance-revised. The original record is preserved intact with an attributed revision notice; it is not silently updated or discarded. Active Objectives, Plans or Operations that relied on that Evidence as primary justification are flagged for revalidation and must not proceed without it; they appear in `urace check` output as blocked on revalidation-pending state. Where revalidation capability is temporarily unavailable, dependent work remains blocked rather than being abandoned or silently continued. Do not restart `urace autonomous` or re-issue an affected Operation while provenance revision is unresolved; doing so risks committing an effect under authorization that is no longer valid.

> **Intent change with committed effects:** When you authorize a change to governing Intent while active Operations have already produced externally committed effects, URACE preserves the prior Intent version as the authoritative basis for reconciling those committed effects. Uncommitted dependent Operations are blocked and will not proceed until an authorized resolution is recorded. Use `urace check` to identify the cross-version inconsistency and the specific Operations held pending. Do not manually edit state files or force-advance Operations to resolve the inconsistency; follow the displayed resolution guidance, which preserves the provenance boundary between the prior and new Intent versions.

> **Goal target reached:** When `urace vitals` shows that an established goal's current metric has met or exceeded its configured target, URACE records the achievement as a durable observation and continues to follow up at the configured cadence to confirm the outcome is sustained. Reaching a target does not automatically close the goal, end lifecycle ownership, or enter dormancy; URACE assesses whether any further justified authorized action remains before converging. To record a terminal closure and formally retire the goal, use an authorized lifecycle operation via `urace help goal`. If no further action is justified and no other pending work exists, the lifecycle converges to dormancy through its ordinary assessment cycle. Do not reassign the same metric to a new goal while a prior achieved record is open without first closing it; doing so creates two overlapping baseline records for the same measure.

> **Goal target revision after baseline recorded:** When an operator revises a goal's configured target after the original baseline measurement is already recorded, URACE preserves the original baseline unchanged and applies the revised target for all subsequent metric comparisons. The revision is recorded as an attributed change to the goal configuration and does not retroactively affect prior progress observations. If a prior observation already met the original target, that achievement record is preserved in durable goal history with the original target as its reference. Use `urace vitals` to confirm the revised target is active before interpreting subsequent progress assessments. Do not revise the target and immediately interpret the resulting delta as evidence of progress or regression; the revised target takes effect from the next scheduled observation cycle.

> **Observation source unavailable:** When a configured metric source for an established goal becomes permanently unavailable, `urace vitals` surfaces a named observation gap rather than reporting a zero value or regression. The last observed value, its timestamp, and the source identifier are preserved as `LAST_KNOWN_GOOD` state. Use `urace add-goal` with an updated observation method to establish a replacement measure with a new, explicitly attributed baseline. Do not interpret the gap as a regression or use the last known value to infer a trend; the Objective status reflects the measurement gap until a replacement is authorized.

> **Observation source schema mismatch:** When a configured observation source is reachable and responding but the configured metric path no longer resolves to a value — typically because an upstream schema change renamed, moved or removed the path — `urace vitals` surfaces a named `source-schema-mismatch` gap, distinct from source unavailability. The last successfully resolved value and its observation timestamp are preserved; the metric is not advanced and is not treated as a zero value or a regression against the baseline. To resolve the gap, supply an updated path through the appropriate `urace` configuration command; the gap persists in `urace vitals` output until an authorized configuration update restores or replaces the affected path. Do not interpret a schema-mismatch gap as evidence of metric regression or source failure — the source itself remains reachable.

> **Observation baseline replaced after gap resolution:** When an operator supplies an updated path or replacement observation source to resolve a `source-schema-mismatch` or `source-unavailable` gap, URACE records the first successfully resolved value from the replacement source as a new, explicitly attributed baseline for that goal. Trend and regression assessments for the goal MUST NOT span the replacement boundary; the prior series and the replacement series are separate attributed measurement lineages. Use `urace vitals` to confirm the new baseline is recorded before treating subsequent observations as continuous trend data. Do not interpret the first post-replacement observation as confirmation of improvement or regression relative to the pre-gap series; it opens a new attributed baseline, not a continuation of the prior one.

> **Baseline observation pending:** When a goal has been registered but its first qualifying observation has not yet been collected, `urace vitals` surfaces a `BASELINE_PENDING` gap rather than reporting a zero value or a regression against a zero baseline. The goal is active and being monitored; no progress assessment is possible until the first successful observation establishes an explicit attributed baseline. This state is distinct from `source-unavailable` — where a previously established source can no longer be reached — and `source-schema-mismatch` — where the source is reachable but the configured metric path does not resolve. Do not interpret `BASELINE_PENDING` as a failure or as evidence that the observation source is misconfigured; it records only that the first qualifying observation has not yet been collected. Use `urace vitals` to confirm when the baseline is established before treating subsequent observations as progress or regression evidence.

## Competing Variants

The portfolio feature compares different approaches to the same goal under equal resource limits. Use `urace help portfolio` for usage.

> **Portfolio inspection:** The portfolio feedback surface is read-only and does not invoke an executor. Use `urace check` or pass the machine-readable output flag to inspect current generation identity, per-variant hard-budget use, guardrail results, Evidence volume and selection confidence while portfolio execution is active. Parent lifecycle feedback distinguishes its own idle state from active delegated portfolio work; `urace check` will not show the system as dormant while a variant is actively executing.

> **Selection confidence:** When accumulated Evidence falls below the portfolio evaluator's declared minimum threshold, the portfolio records `INSUFFICIENT_EVIDENCE` as that evaluation cycle's terminal disposition — not a guardrail failure and not a variant regression. Variants carrying this disposition remain eligible for reassessment when qualifying Evidence arrives within applicable resource ceilings; their gap records are preserved as lineage. Use `urace check` to distinguish `INSUFFICIENT_EVIDENCE` from `GUARDRAIL_FAIL` or `SELECTED` dispositions when reviewing portfolio results.

> **Portfolio cycle with no eligible result:** When every variant in a generation carries `GUARDRAIL_FAIL` or `INSUFFICIENT_EVIDENCE` at the evaluation boundary, the portfolio records no selection for that cycle. The parent lifecycle does not treat this as a system failure; the generation closes with its dispositions intact and lineage preserved. Use `urace check` to inspect the cycle's dispositions and resource use before deciding whether to add goals, adjust guardrails or re-run.

> **Past portfolio generation results:** Completed portfolio generations remain in the durable portfolio ledger after their cycle closes. Use `urace help portfolio` for the command that lists past generation identities, per-variant dispositions, resource use and selection rationale. Inspecting past generations does not require re-running any generation or invoking an intelligent Executor. `urace check` surfaces only active or interrupted generations with unresolved state; for retrospective review and trend analysis across completed cycles, use the portfolio history command. Non-selected variant lineage and lessons from past generations are preserved as advisory Evidence for subsequent generations and appear in the history output.

> **Non-selected variant lineage:** When a variant is not selected, its lineage, observations, failure Evidence and uncertainty-qualified lessons are preserved as durable portfolio records. A later generation MAY inherit these findings as advisory Evidence when the inherited context is independently validated and attributable to its source variant. Use `urace check` or `urace help portfolio` to inspect which lessons from prior non-selected variants were considered for the current generation. Non-selection implies neither universal inferiority nor ineligibility for future inheritance; it records only that a specific variant was not the preferred candidate under the conditions at evaluation time.

> **Interrupted portfolio generation:** When `urace autonomous` stops — through a signal, crash, or resource exhaustion — while a portfolio generation is in progress, the lifecycle preserves completed variant work and records each variant's last committed state. `urace check` exposes the interrupted generation's identity, the completion status of each variant up to the interruption, and whether any variant has unresolved effects requiring reconciliation before the generation can proceed. An interrupted generation is not a failed generation; resuming `urace autonomous` continues each variant from its last safe lifecycle boundary rather than restarting the generation. Do not initiate a new portfolio run while `urace check` reports an interrupted generation with unresolved variant state; doing so opens a second generation lineage and discards incomplete variant work from the first.

> **Cancelling an active portfolio generation:** Stopping `urace autonomous` while a portfolio generation is in progress creates an interrupted generation, not a cancelled one. An interrupted generation is resumable: a subsequent `urace autonomous` run continues each variant from its last safe lifecycle boundary. To intentionally discard a generation rather than resume it, use the portfolio cancellation command identified in `urace help portfolio`; cancellation records a terminal disposition for each variant at its current state, closes the generation lineage, releases reserved resources and marks the generation non-resumable. A cancelled generation is not automatically resumed by a subsequent `urace autonomous` run. Use `urace check` before starting a new generation to confirm whether the current state is interrupted (resumable) or cancelled (terminal); starting a new generation while an interrupted one is unresolved opens a second generation lineage and discards incomplete variant work from the first.

> **Inbox inputs queued during active portfolio generation:** Mutating commands queued while a portfolio generation is actively running — including `urace add-goal`, `urace update apply`, configuration changes and similar — are preserved in the atomic inbox and are not applied to the running generation. They take effect at the next safe lifecycle boundary after the generation completes or is interrupted; the active generation is not retroactively affected. Do not assume a queued command is immediately visible to the running variant; do not re-issue an identical command assuming the first was lost — a preserved inbox entry will be applied a second time if re-issued. Use `urace inbox list` to confirm receipt. If a queued command is time-sensitive relative to the generation outcome, inspect generation progress with `urace check` before deciding whether to wait for completion or cancel the generation first.

> **Portfolio adapter requirement:** Portfolio evolution uses Product-specific adapters to create isolated variant environments, run candidates and evaluate results. For the URACE blueprint Product, built-in adapters are present. For other Products, the portfolio controller checks for compatible adapters before a run can be initiated; missing adapters surface as `ADAPTER_REQUIRED` in `urace check` and `urace help portfolio` output. A portfolio run cannot proceed until required adapters are installed and validated. Adapter installation is an authorized environment change that does not alter the frozen experiment constitution of an already-initiated generation.
